## 本轮最小原型

外部程序原子发布固定请求 → 原生 `AddMainThreadPeriodicTask` 主线程回调
检测文件 → 写回带 session、request ID、slot 和执行计数的结果。
注册脚本正常路径中没有阻塞等待；停止文件、最长存活时间和回调次数都有界。
这里只实现固定 ping、合成图 stats 和无副作用的 fail，不接收脚本代码。

Gatan [官方文件等待示例](https://www.gatan.com/sites/default/files/images/scripts/Having_a_script_wait_for_a_file_to_appear.s)
证明原生主线程定期检查文件是受支持的 API 用法。该示例随后无限等待信号，
本实验没有采用这一部分。官方 API 的存在不能代替本实验的注册返回、对象存活、
停止清理、Python 共存和数值结果验收。

## 即使入口通过，仍需补齐的边界

- 此时只能证明一个小型原生文件入口，无 Python serve loop；不能直接推断
  Python 监听器可在任意用户脚本运行时安全重入。
- 32 个顺序槽只用于有限实验；客户端预留后崩溃可阻塞后续槽。没有自动填洞、
  超时重发、通用调度器或崩溃后 exactly-once 承诺。
- TTL 在下次回调检查，不能中断被阻塞的 UI 或已经开始的原生 I/O/计算。
- 本地目录不是鉴权边界；原生 MoveFile 的文档也不证明所有文件系统上的
  原子可见性。客户端继续校验完整结果，未知状态不冒充失败或停止。
- 大数据、其他 GMS 版本、性能、长期运行和生产工具迁移均未验证。

若注册和闭环通过，下一步只做：独立 Python 执行前后 ping、暂存文件不触发、
多个排队请求与重复 ID、固定合成图 stats、停止及移除验证；之后单独研究
有限 busy 时段中的 Python 监听器触发。生产 Bridge 继续保留。
